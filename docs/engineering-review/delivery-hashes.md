# Область хэшей опубликованной поставки

Исправление после принятия содержательной части issue #3. В исходной публикации
`fadedbab0a4040630906d23857354be9bd4aa40c` 16 из 37 source/artifact SHA
были вычислены по CRLF-байтам Windows. Git хранит соответствующие файлы с LF.
Это ошибка привязки поставки; она не означает изменение геометрии или результатов
контрольного опыта. Прежнее независимое ревью подтверждало локальные байты,
а не эти опубликованные Git-привязки.

## Текущая поставка

В [acceptance.json](acceptance.json) только карты `source_sha256` и
`artifact_sha256` являются хэшами опубликованных файлов:

- SHA-256 вычисляется по исходным байтам Git blob, без декодирования,
  CRLF/LF-преобразования, `autocrlf` или иного фильтра рабочего каталога.
- Проверяющий один раз разрешает переданный Git ref в полный commit SHA.
  Manifest и все цели обеих карт читаются из этого же commit через `git show`.
- Проверяется перечисленный набор: 18 source и 22 artifact, всего 40 файлов.
  Это прежние 37 целей плюс этот документ, verifier и архив Windows-снимка.
- Manifest не хэширует сам себя. Это не хэш полного дерева репозитория:
  неперечисленные файлы, включая GOAL и журнал последующей проверки, не входят
  в заявленную область. Полный SHA проверяемого commit и SHA самого manifest
  сообщает verifier; commit служит внешней опорой для его чтения.

Проверка после обычного fetch опубликованной ветки, через Windows executor:

```powershell
git fetch origin work/issue3-engineering-patterns
.venv/Scripts/python.exe -B docs/engineering-review/verify_delivery.py --ref origin/work/issue3-engineering-patterns --output output/delivery-verification.json
```

Запускать из checkout этой ветки с существующим каталогом `output/`, либо
опустить `--output`. Скрипт использует только stdlib и Git, не строит модели
и не запускает тесты. Он проверяет raw blobs даже в рабочей копии с CRLF.
Для воспроизведения исторической проверки нужен также исходный commit выше
(обычный полный clone его содержит).

## Исторический опыт

[windows-execution-snapshot.zip](evidence/windows-execution-snapshot.zip)
сохраняет 38 файлов: исходный Windows `acceptance.json` и точные Windows-байты
всех его 37 source/artifact целей. Они взяты из сохранённого снимка, не
реконструированы заменой LF на CRLF. Сам ZIP связан новой картой artifact.
Verifier отдельно проверяет его CRC, все 37 первоначальных привязок и равенство
значений исходного manifest его первоначальной Git-публикации. Представления
файла manifest в ZIP и Git при этом намеренно различаются переводами строк.

Остаются историческими и не являются картой текущей Git-поставки:

- `protected_main_sha256` и вложенные сведения `pytest` о локальной проверке;
- SHA внутри `measurements.json`, `before-argv.json`, `read-inputs.json`,
  `pilot-input-sha256.json`, `input-provenance.json`, `regression.json`;
- внутренние привязки `pilot-input.zip` и `filter-control.zip`.

Их значения, прежние ZIP, исходники, измерения и результаты опыта не
перезаписываются. Вложенные SHA относятся к названным в них историческим
байтам/снимкам. Хэш текущего Git-файла, содержащего такой JSON или ZIP,
проверяется отдельно внешней картой artifact. Подмена внутреннего исторического
SHA новым Git-хэшем исказила бы evidence опыта.
