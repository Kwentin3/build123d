# Работа с CAD

Выбирай только затронутые шаги. Для изменения отверстия обычно достаточно
задания → правки параметра → измерений/экспорта → отчёта. Новое изделие
и производственный выпуск требуют большего объёма.

| Шаг | Что должно быть понятно для перехода дальше |
| --- | --- |
| Требования | Назначение, размеры/единицы, обязательные свойства и артефакты; неизвестное явно отмечено |
| Подход | Существующая модель/операции подходят; предметные ограничения остаются у изделия |
| Геометрия | Редактируемый Python, именованные параметры, валидное ожидаемое число тел |
| Сборка, если нужна | Положение, контакты, зазоры, пересечения и допустимая последовательность движений |
| Проверка | Фактические измерения против задания, отрицательные случаи, STEP после импорта |
| Производство, если нужно | Выбран процесс; контуры, единицы и количества проверены; непроверенный fit указан |
| Выпуск | Только текущие файлы, отчёт с хэшами, ограничения и необходимые документы |
| Изменение | Зафиксирована новая цель; повторены зависимые проверки; старый отчёт не принят как текущий |

На переходе **Требования → Подход** выбери проверки по затронутой функции:
зачем существует узел, в каком состоянии он работает/обслуживается, как может
утратить функцию и какой вход нужен для проверки. Для крепления сначала
определи соединяемые детали, фурнитуру, опоры и доступ; для сопряжения —
контрагент, базы и предельные размеры; для обслуживания — допустимую разборку
и путь. Важные допущения не становятся требованиями только потому, что модель
и тест повторяют их. Уточняй критические неизвестные, продолжая независимую
работу. Не назначай крепёжную функцию по одному круглому отверстию.

Условные паттерны выбираются через [cad-entry](.agents/skills/cad-entry/SKILL.md).
В существующем задании/README и отчёте достаточно связи «требование/источник →
возможный отказ → проверка и её область → evidence → вывод/пробел».
PASS относится только к проверенному свойству; FAIL — к нарушенному явному
требованию или обоснованному критерию; отсутствие нужных данных — NOT_CHECKED
с причиной и следующим действием. Необъяснённая особенность без критерия —
инженерное замечание для разбора. Технический сбой выделяй отдельно.
Пересечение вырезов не является универсальным запретом; оцени функцию,
материал и путь передачи нагрузки. Полный каталог проверок каждой малой правке
не нужен, но обязательные непроверенные свойства не должны исчезать из вывода.

FAIL возвращает к конкретному параметру, построению, размещению или экспорту.
Техническая ошибка возвращает к неисправной операции; она не доказывает
инженерного дефекта. NOT_CHECKED читается вместе с причиной: обязательную
проверку нужно выполнить, необязательную — честно оставить открытой.

Измеренные свойства не подменяют требования. Не исправляй тест изменением
ожидания только ради PASS. BREP-valid, правильный объём и снимок подтверждают
разные вещи. Геометрия не доказывает прочность, термостойкость или натурную сборку.
В мангале есть геометрические sweep-проверки поступательных траекторий
с ограничениями поверхностей; это не физическая динамика.

Для каждого изменения:

1. Прочитать выбранную модель, задание и Git diff. Выбрать необходимые Skills.
2. До правки сохранить принятую исходную редакцию и геометрию. Записать, что
   разрешено менять, что защищено, какие сопряжения и проверки затронуты.
   Править минимальный участок. Для испытания — отдельная копия/каталог output.
3. Запустить прежний CLI, прочитать свежий `report.json`, затем тесты модели
   и `.venv/Scripts/python.exe -m pytest -q` (Linux: `.venv/bin/python`).
4. Сопоставить measurements/expected с заданием, разобрать FAIL и NOT_CHECKED.
   Сравнить с принятой геометрией: ожидаемое, обоснованное сопутствующее и
   непреднамеренное. Последнее блокирует приёмку до исправления и перепроверки.
   Проверить хэши входов и файлов. При изменении условий повторить затронутую проверку.
5. Если запрошена визуальная приёмка, получить `--screenshots` в существующем
   viewer и открыть новые PNG. Не переносить старый visual review на новую редакцию.
6. Обновить существующую запись задачи: принятое решение, evidence,
   незакрытые пункты и следующий шаг. Убрать только свои временные ресурсы.

При новой сессии начать с AGENTS.md → cad-entry → README конкретной модели,
задания и Git diff. Сравнить хэши отчёта с файлами; при несовпадении или
отсутствии привязки повторить нужный запуск. Восстановление не требует истории
чата, если исходные требования и решения сохранены рядом с проектом.

## Передача отдельной работы

Для изучения существующего изделия идти от списка деталей/движений к узлу,
его параметрам и использованиям, затем к нужной геометрии. Для отверстия
повторить его измерения, защищённое тело и STEP/STL/отчёт; для паза сборки —
ещё сопряжённые детали, зазоры, коллизии, всю зависимую последовательность
движений, STEP/DXF и документацию. Изменение размещения требует сравнения
мировых положений. При неясной зависимости проверять шире. Этот выбор
направляет исследование и не отменяет обязательный полный pytest.
Примеры узких контрактов: [local-edits.md](.agents/skills/cad-validation/references/local-edits.md).

Основной агент сохраняет цель изделия, решения пользователя и приёмку общего
результата. Передавай исполнителю самостоятельную работу с ясной границей.
Название профессии и Skill сами по себе не заменяют задания.

Обычным текстом укажи цель и критерии готовности, точные входы/редакцию,
существенные зависимости и ограничения, допустимые изменения и нужный выход.
Ссылайся на существующие требования; не создавай их второй пересказ с другими
размерами. Для короткой работы достаточно сообщения. Файл задания нужен,
только если его полезно сохранять или повторно использовать.

Исполнитель возвращает краткий результат: что сделано, где файлы, что и как
проверено, отклонения и недостающие данные. Подробности остаются в артефактах.
При отсутствии существенных требований запроси их у основного агента;
не угадывай допуски и не расширяй полномочия. Основной агент проверяет
совместимость результата с соседними деталями и актуальность входов.

Для самостоятельной задачи или независимой проверки используй штатный новый
контекст. Если продолжение требует существенной истории решений, передай
её или нужные первоисточники. Общие инструкции, Skills и tools могут
загружаться host отдельно от задания; отсутствие истории не означает пустой
вход модели. Не допускай одновременной записи в одну общую модель.

Один пример подтверждает только применимость передачи к этому примеру.
Меньший текст не доказывает меньшую стоимость или лучшее качество: учитывай
всех исполнителей, повторное чтение и координацию. Добавляй правила по
наблюдаемым пробелам, не превращая особенности одного изделия в общий процесс.
